# RBAC permission matrix (generated from the controllers and role definitions)

Generated by scanning `@RequirePermissions` on every controller route plus `owner-role.ts` / `system-roles.ts`. It states what the code does today; it is not a proposal. Re-generate when routes or roles change (`legacy-enforcement.spec.ts` and `controllers-authenticated.spec.ts` fail if enforcement drifts).

## 3. Roles

| Role | How its access is computed | Notes |
|---|---|---|
| Owner | stored legacy permissions (all administrative ones) + all granular grants by definition | one per organization; created only by the operator CLI; cannot be assigned/edited/deleted via the API |
| Admin | stored legacy permissions (same set as Owner) | granular config for Admin only limits what it may **delegate** when creating custom roles; it does not narrow Admin's own legacy access |
| Analyst | stored legacy permissions (read-only set) | unchanged |
| Employee | stored legacy permissions (`sessions:read`, `responses:write`) | unchanged |
| Custom | derived at request time from its grants through the six exact mappings; stored legacy `permissions` are ignored | assigning/editing/deleting custom roles needs the matching `roles.*` grant *and* legacy `roles:write`/`users:write`, which no custom role can hold |

Permissions are re-read from the database on every request (`JwtStrategy.validate`); token claims are never trusted.

## 4. What the frontend uses for show/hide (not security)

`contacts:write` (contacts page), `sessions:write` (create-session button), `sessions:launch` (wizard launch),
`users:write` (role dropdown in User Management), `roles` API flags `canCreate/editable/deletable` (Roles & Permissions).
Everything else relies on the API refusing the request. The UI values come from `/api/auth/me` and the role API; the API is the authority.

## 5. Test coverage

* Routes ↔ legacy keys are pinned by `legacy-enforcement.spec.ts`; every controller is JWT-guarded (`controllers-authenticated.spec.ts`).
* Exercised end-to-end against real guards (integration suites): `users.read`, `roles.read` (custom role), all `roles:*`/`users:*` routes for Owner/Admin/Analyst/Employee.
* The other four effective grants (`contacts.import`, `sessions.launch`, `templates.read`, `ai.use`) are covered by the mapping unit tests and the pinned decorators, **not** by a live request, because those controllers' modules are not loaded in the integration harness. This is a known gap.
